# Lichess Woodpecker

Vanilla-JS browser extension (no build step, no runtime deps). Saves Lichess puzzle IDs into categories and runs Woodpecker-style randomized training with an on-page overlay. Chrome MV3 is primary; Firefox MV2 is supported and must not regress.

## Architecture
- `background.js` — service worker; owns all storage CRUD on `lichessNotes` (`{categories: {name: [puzzleId]}, meta}`; `meta.categoryMeta[name] = {color?}` holds a palette index, kept in step by create/rename/delete (rename carries it over; saving never touches it); categories predating colours show `hashColor(name)` and are never written just by being read; the export does not include `categoryMeta`) and routes messages: `GET_ALL_DATA`, `CREATE_CATEGORY`, `RENAME_CATEGORY`, `DELETE_CATEGORY`, `ADD_PUZZLE`, `REMOVE_PUZZLE`, `RECORD_STATS` (the overlay's finished cycle) and `CLEAR_STATS` (the options page), `OPEN_OPTIONS_PAGE`, `IMPORT_PREVIEW` and `IMPORT_APPLY` (see Import), plus `GET_SESSION_ROLE` and `CLAIM_SESSION` (see Session ownership). Returns `{ok, error?}`.
- `popup.*` / `options.*` — UI; talk to background via `browser.runtime.sendMessage`. **The options page** is a sticky top bar (`.topbar`: title, the **Backup & Restore** button and the tabs) over two ARIA tabs, **Categories** (the default: two stat cards, then search, New Category, the list; the cards are `renderTotals()`: how many categories, and how many *different* puzzles, de-duplicated across categories, recomputed on every `refreshUI()` from the whole library so a search never changes them) and **Statistics** (`#panel-stats`: Clear Stats, and the 10 most recent cycles by completion date with a **Load more** that adds 10 and a "Showing N of M" count; storage order is never trusted, and the list is only paginated, not charted). Layout: an icon tile and "Training History" with Clear Stats on the right (no Refresh button: the page syncs itself, see above); the table in its own rounded, bordered box with compact rows (about 33px), single-line headers, each with an icon (Category folder, Time clock, Puzzles piece, Correct circled check, Incorrect circled cross, Skipped skip-forward, Accuracy target; the date has none) and thin dividers between columns, the category and date left, every figure centred; the figures follow one colour system, on the header icons and on the numbers alike: **Correct green `#22c55e`, Incorrect red `#ef4444`, Skipped amber `#f59e0b`, Accuracy neutral `#e2e8f0`** (`--stat-*`), while the accuracy *values* stay traffic-light by rate. The widest realistic row ("All Categories", `5m 41s`) must fit with no sideways scroll, and the widest *date* is `Yesterday, 11:09 AM` (wider than `Today, 11:22 AM`, which an earlier test used, so every user saw yesterday's rows clipped); the header cells set the column widths (`nowrap` plus an icon), so their side padding (5px) is what keeps all four date shapes inside the 760px page, and a test seeds one of each. The overlay's own score row still colours Incorrect amber and Skipped red, the reverse of this table: a known inconsistency, to align deliberately if wanted; the count and Load more in a bar of their own. Durations use plain tabular figures, not monospace. **The page follows storage live** (`watchStorage()`): any write to `lichessNotes` from elsewhere (the popup's Save/remove, a training cycle that just ended, an import in another tab) arrives via `storage.onChanged`, is coalesced over 60ms, and re-runs `refreshUI()` and `loadStats()`, so nobody has to reload. `refreshUI()` rebuilds the category list only when `[categories, search]` actually changed (`renderedList`; a finished cycle changes only the statistics, so the list node is left untouched) and it puts back whichever categories were open, so neither a sync nor your own removal of a puzzle folds a category shut; open dialogs, the search text and "Load more" are left alone. This relies on `browser.storage.onChanged`, which current Chromium and Firefox define themselves but the Chrome polyfill (`browser-polyfill.js`) must expose for older Chrome; a test runs the polyfill with no `browser` defined to prove it does. A **Help & About** button (`#btn-help`, a `?` beside Backup & Restore; deliberately not in the popup, which stays about saving and training) opens `#help-overlay`: the logo on its tile, four links (Help & Documentation → the GitHub README, Report an Issue → the repo's Issues, Contact Developer → a `mailto:` to the public address already in the README and privacy policy, Privacy Policy → `PRIVACY_POLICY.md` on GitHub) and the version read from the manifest, as the page footer's is. They are plain links: web ones are `target="_blank" rel="noopener noreferrer"`, the mailto has no target (it would open an empty tab), nothing is fetched or sent, and no permission is involved. If the repository is ever renamed or moved, update these four URLs (a test pins them). Import and Export live in the Backup & Restore dialog (`#backup-overlay`); the file input `#import-file` stays page-level, and choosing a file closes that dialog before the import preview opens. Clear Stats asks with an in-page dialog (`#clear-overlay`, Cancel focused, Escape cancels), never `confirm()`, for the same reason as the overlay's Restart. **Deleting a category has no dialog: it is two clicks on its bin** (`handleDeleteClick`): the first arms it (`.armed`: red icon in a red-tinted box, title `Click again to delete "NAME"`, the same words in `#sr-status`, a visually hidden live region, for screen readers), the second deletes. It disarms after 4s, on a click anywhere else, on Escape, when focus leaves it and when another bin is armed; the page-level rules exist because Safari and Firefox on a Mac don't focus a button on click, so focus loss alone would not cover them. A second click within 400ms is ignored (a reflexive double-click must arm, not delete: this is irreversible). Tests check each rule *immediately*, never with a patient `expect`, because the 4s timer would rescue a missing rule inside Playwright's 5s wait. **Look**: a deep navy page (`--page-bg`: a soft glow at the top left over a vertical gradient, `background-attachment: fixed` so it stays put however long the list is) with layered surfaces (`--sheen` highlight, soft blue-tinted `--border`, one `--shadow`); the sticky bar must stay **opaque** so the list never shows through its text, so it is painted with the page's own fixed `--page-bg` (seamless, not a darker box) rather than made translucent. As in the popup, a gradient is always a translucent layer over a solid colour. Red *text* uses `--danger-text` (lighter than the button red) to stay above 4.5:1, and a test measures the contrast of the title, tabs, stat cards, rows, table and dialog text. Popup also writes `trainingSession`. The popup is state-driven: `data` (stored categories + metadata), `currentPuzzleId` and the search drive `renderAll()`; under the puzzle card a slim `.summary` row shows two library-wide totals (`renderSummary()`: how many categories, and how many *different* puzzles, de-duplicated across categories, so one puzzle saved in four categories counts once), which a search never changes and which every save or remove refreshes; there is no "Categories" heading any more, and the puzzle ID in the card is deliberately small; Save updates rows **in place** (`syncRows()`) so a row never moves under the pointer. Only the category list scrolls (`.popup-container` is a flex column 380px wide and capped at 475px, so about five rows show whether there are 5 categories or 100; rows are 41px, the Save/Train buttons 32px, Train all 37px). The width is 380 rather than a tighter 360 on purpose: at 360 a long name beside a count and a `⏸ 87/200` tag was squeezed to ~52px, so a test keeps such a name at 80px or more. Train's hover/focus expansion is a `train-hot` class set from pointer/focus events, not `:has()`, because Firefox 109 predates `:has()` (121). Per-puzzle open/remove lives on the options page only. **The popup shows the running cycle too**: `loadData()` reads `trainingSession` into `data.running` (same rule as the options page: no `pausedAt`, no `cycleFinishedAt`), and that row's Train bolt (or the Train all bolt, for `All Categories`) is gold `#fbbf24` (`.is-running`). It is read when the popup opens; the popup is short-lived, so there is no live watcher. **The Categories toolbar** is two rows: right-aligned **Train all categories** (`#btn-train-all`, the same `.btn-train` look: it keeps its label for a parked `All Categories` cycle (the tooltip says it will continue), has the gold bolt while that cycle runs, and is disabled with no puzzles; it trains one cycle over every *different* puzzle) and **+ New Category**, then the search box on its own, full width. A test pins the order (a button row above the search). **Searching opens the categories that match** (`renderedFilter`): when the search text changes, every shown card is open, and clearing the search closes them all again; a sync while searching (same text) keeps what you opened or closed by hand. `paintTrainButton()` draws every Train button; a category with no puzzles has it greyed out (`aria-disabled`, opacity .45, tooltip "Save a puzzle before training.") as in the popup, and a press still toasts "No puzzles to train." (tests must `click({force: true})` it). **Train from the options page**: each category row has a labelled button (`.btn-train`: a lightning bolt and "Train" in neutral navy with a subtle border; it **always says Train**, even with a parked cycle: the amber `⏸ n/total` tag after the count says it is paused, and Train continues it, as in the popup; then a divider, then Rename and Delete). The page reads `pausedCycles` in `refreshUI()` (part of the rebuild key) and watches it as well as `lichessNotes`, so a cycle paused in the overlay flips the button live. The category being trained *now* (`trainingSession` with no `pausedAt` and no `cycleFinishedAt`) gets `.is-running` (so "running" means an unfinished, unpaused session is stored; one whose tab closed still counts until resumed or ended): a gold bolt (`#fbbf24`); pressing it starts a fresh cycle like the popup's Train, replacing the running one. The button runs `trainCategory()`: it continues the category's parked cycle or starts a shuffled one, opens an `about:blank` tab, has the background set the session with that tab as owner (`START_SESSION`), *then* points the tab at the puzzle (the same order as the popup, so the overlay finds its owner and shows no Resume chip). It builds the session with the shared `buildSession()`, as the popup does. An empty category toasts and opens nothing. With no puzzle detected (`.is-unavailable`) the card is a compact single row (about 34px, well under the full-size card, so a detected puzzle clearly dominates): "No puzzle detected" on the left and, on the right, a standalone link "Open Lichess puzzles ↗", a real `<a href="https://lichess.org/training" target="_blank" rel="noopener noreferrer">` (not a link buried in a sentence) whose `::after` stretches over the whole card, so the whole card is the click target; a plain link needs no permission (no `tabs`, no host access) and works in Firefox. **Following it closes the popup** (`tabs.create`, then `window.close()`; modified clicks are left to the browser): Chrome closes the popup when the new tab takes focus, but Firefox leaves it open, and an open popup cannot read the new tab (checked in Firefox 157: `Missing host permission for the tab`, because `activeTab` covers only the tab the popup was opened on), so it sat saying "No puzzle detected" over a puzzle until it was closed and reopened by hand. Reopening it on the puzzle tab works, as that is a fresh toolbar click. Reading the new tab from the open popup would need host access to lichess.org, which was deliberately not added. The two card sizes differ on purpose: the popup waits for tab detection before its first render, so it is drawn in its final state and nothing jumps. The reason Save is off is in its tooltip ("Open a Lichess puzzle to save it"). **Popup look**: deep neutral blue-gray surfaces (`--bg`, `--bg-card`, `--bg-elev`, `--bg-hover`; no purple cast) layered with a faint top highlight (`--sheen`), soft translucent 1px borders (`--border`), one restrained shadow (`--shadow`) and radii of 7-9px; type is 11-13px at weights 500-600 (the totals' numbers 15px). **Every gradient is a translucent highlight laid over a solid colour** (`background: var(--action-sheen), var(--action-bg)`), never a gradient alone, because the colour tests read `background-color`, and a gradient-only background would read as transparent and silently pass or fail the wrong things. The puzzle card stays green-tinted whenever a puzzle is detected (saved or not) and neutral only for "none open"; New and Train all are filled blues (`--fill-*`) and Save is the deeper navy with a bright blue edge (`--action-*`), so a test also keeps Train all blue, not neon, and readable. **Colour means one thing in the row buttons**: green is only "already saved" (a bare circled check with no container), an available `Save` is the action blue (`--action-*`), and Train is neutral even when expanded; a test fails if an available Save or an expanded Train turns green, or if the Save/Saved/Train colours drop below 4.5:1. **Save is a toggle**: the saved check turns into a subtle red ⊗ on hover or keyboard focus (tooltip "Remove from this category", accessible name "Remove ID from NAME") and clicking it sends `REMOVE_PUZZLE`; if the puzzle was already removed elsewhere the popup just catches up with a warning, not an error. Its word "Saved" stays in the DOM, collapsed, for screen readers and tests. Both save and remove refresh the row counts, the puzzle card and the Train all footer (saving the first puzzle used to leave Train all disabled until the popup was reopened). **Neither shows a toast**: the row turning to Saved (or back to Save) is the confirmation, so a green "Saved to X" / "Removed from X" bar was only noise; it is announced to screen readers through a visually hidden live region (`#sr-status`) instead, and the toast is kept for news: "Already in X", "Not saved in X any more" and errors (a test reads the toast *immediately*, since a success toast hides itself and would pass a patient check).
- `content.js` + `content.css` — overlay on `lichess.org/training/*`. Reads `trainingSession`, writes stats into `lichessNotes`, and owns `overlayPos` (`{left, bottom}`, the dragged position; defaults to bottom-left so it doesn't sit on Lichess's hint/controls). Uses `chrome.*` callbacks. Depends on Lichess DOM (`.puzzle__feedback.after`, `.continue`, `.vote`, `.puzzle__session a.current`, `.puzzle__moves move.fail/.win`) — the most fragile part. **What the overlay trusts from the page, and what the page can do to it** (reviewed): the page's markup is read for *booleans only* (is the finished panel showing, did a move fail, which result class the strip has) and none of it is ever put into `innerHTML`, so a hostile page can at worst make the stats wrong or move the cycle along early, which only affects the user's own counts. There is no `message` listener and no page-facing API, so page scripts cannot talk to the extension; its messages to the background are limited to what `OVERLAY_MAY` allows; and the places it navigates to come from the stored queue, which the background only accepts as `https://lichess.org/training/<id>`. What it does not hide: the overlay is ordinary DOM in the page (`#lpn-woodpecker-overlay`), so lichess.org's own scripts can see that the extension is installed and read what is shown in it (category name, progress), and can click its buttons. A closed shadow root would stop that, at the price of reworking every selector and test; not done. **Cleanup**: `detach()` removes every observer, timer and listener the overlay adds (a test counts the listeners left on `window` and `document` through the DevTools protocol, in the extension's isolated world, after a detach and after the Resume chip is dismissed; it found a `resize` listener that was never removed and a chip whose dismissal left listeners and the theme observer running). Anything new the overlay attaches must be removed there.
- `browser-polyfill.js` — gives `browser.*` promises on Chrome.
- `slam.js` — **EXPERIMENT (branch `experiment/slam-board`)**: **Shift+F slams the board** on puzzle pages: the board rises, drops with a synthesized thud (Web Audio, no audio file), the page's `main` shakes, a cloud of dust (`[data-wpk-slam-dust]`, fixed, `pointer-events: none`, removed when it ends) is thrown up along the board's lower edges, and every piece bounces, wobbles and tilts, rippling out from the middle, then settles exactly on its square. A second content script, separate from `content.js` because it must work on every puzzle page (including with no session of ours, where `content.js` installs nothing); listed in both manifests' `content_scripts` and both `INCLUDE` lists, with no new permission and the same `https://lichess.org/training/*` match. Rules, each pinned by `tests/slam.spec.js`: only Shift+F (by `code`, no Ctrl/Alt/Meta, no key repeat, ignored in inputs, textareas, selects and contenteditable, and plain F stays Lichess's flip); **no lock: every press slams at once**. A press while the last slam is still playing cancels that slam's board, shake and wobble (two animations of one property replace each other, they do not add) and starts a fresh one with a quick wind-up (`REPEAT_IMPACT` 110ms against the first press's 300ms: the board keyframe offsets are `ms / total` from `impact`, with a fixed 700ms settle), while its dust keeps fading; at most 3 dust clouds live at once (the oldest is removed), and every thud goes through one shared `DynamicsCompressor` so stacked thuds do not clip; a held key (`repeat`) is still ignored; nothing at all (no motion, no sound) under `prefers-reduced-motion`; nothing and no error when there is no board; it animates **only the individual `translate`, `rotate`, `scale` and `opacity` properties, never `transform`** (chessground places every piece with an inline `transform`), through the Web Animations API so everything cleans itself up (no timers, no listeners to remove, no inline style left; the test compares every piece's style and box before and after). **A piece's `rotate` turns it about the middle of its UNplaced box, the board's top-left corner, not about its own centre** (the matrix is translate·rotate·scale·transform), which first threw far pieces more than 100px around the board; each tilt therefore carries the translation `(I - R(angle))·(x, y)` read from the piece's computed `transform`, and a test bounds how far a piece strays mid-wobble (it fails at 90px without the correction). Fail-safe: the whole slam is in a `try`, and on any error it cancels what started and removes the dust (a test breaks `DOMMatrixReadOnly` in the extension's world and checks Shift+F works again; note `animation.finished` must not be read after `cancel()`: it is then a new promise that never settles, which once left a lock stuck forever; there is no lock now, but a slam still never waits on `finished` after a cancel). A piece chessground is sliding (`.anim`, `.fading`) is left out, because its tilt is worked out from where it stands at that moment; a piece that moves mid-slam anyway would be off by a bounded amount until its 0.9s wobble ends (cosmetic, not tested). Shift+F is unbound on Lichess (checked live: Shift+F leaves the orientation, plain F flips it). The audio context is created on the key press and reused; a throwing or missing `AudioContext` leaves the visuals running. To remove the feature, delete `slam.js` and its line in the two manifests and the two package lists. Not in the store listings or the privacy policy (it sends and stores nothing).
- `shared.js` — loaded by `popup.html` and `options.html` (after the polyfill, before their own script) for what both pages must do the same way and cannot import (no build step): `buildSession(name, pool, trainingSession, pausedCycles)` → `{session, park, unpark}` (a fresh shuffled cycle, a parked cycle continued with its clock shifted, or an old-shape paused cycle parked/continued; pure, the caller sets `ownerTabId` and sends `START_SESSION`), `fisherYatesShuffle` and `showToast`. Neither page may redefine them (a test fails if one does). Never load it in the overlay (it would have to be listed in `content_scripts` in both manifests) or the background. The overlay keeps its own copy of the shuffle on purpose. A new shared function goes here, not into a second page.
- `manifest.json` (MV3) and `manifest-firefox.json` (MV2) — must stay in sync.

## Rules
- Change both manifests together (version, permissions, content_scripts, description). `npm run check` enforces it.
- Chrome Web Store description ≤ 132 chars.
- User data (puzzle IDs, category names, imported text) goes into the DOM with `textContent` or `setAttribute`, never into an `innerHTML` template: the pages and the overlay build their rows that way, and `innerHTML` is only for static strings (the SVG icons). There is no `escapeHtml` helper (this rule used to name one that no file defined). A test fails if a `${}` appears inside an `innerHTML` assignment in `popup.js`, `options.js` or `content.js`.
- No new permissions or host access without saying why. No remote code, no analytics. Permissions are exactly `storage`, `activeTab`, `scripting`: the `tabs` permission was removed on purpose (it exposes every tab's URL, shown as "read your browsing history"), since only `tabs.query/update/create/get/onRemoved` are used and none need it. A test fails if tab URLs become visible again.
- No Chrome-only APIs (sidePanel, offscreen, …) without a Firefox fallback; MV3-only manifest fields need the MV2 equivalent.
- **The content script matches exactly `https://lichess.org/training/*`** (no `http`, no subdomains: it was `*://*.lichess.org/training/*` up to 1.2.1). It is the extension's only standing site access, so it should be no wider than the privacy policy says; `npm run check` fails on any other pattern, and a test shows the overlay does not appear on `www.lichess.org`. Note the pattern needs the slash, so the bare `/training` page itself has no overlay (the popup still reads it, through `activeTab`).
- **`manifest-firefox.json` must keep `browser_specific_settings.gecko.data_collection_permissions`** (`{"required": ["none"]}`: the extension sends nothing anywhere). Mozilla requires it of every new add-on from 3 Nov 2025 (a new add-on without it is rejected when AMO signs it), and once a version declares it every later version must too; `npm run check` enforces it. `web-ext` is pinned at 10.7.0 (addons-linter 10) for this reason: 8.9.0's linter (7.18) reported the key as an *error* (`DATA_COLLECTION_PERMISSIONS_PROP_RESERVED`) and never complained when it was *missing*, so its clean lint proved nothing about AMO. If the extension ever transmits data anywhere, change `required` and `PRIVACY_POLICY.md` (and its copy in `docs/privacy-policy.html`) together.
- **Store listings** live in `docs/store/` (`chrome_web_store_listing.md`, `firefox_addon_listing.md`, the promo images) with the screenshots in `docs/screenshots/`. They are the text and assets to paste into the two stores' dashboards, so when a feature, a permission or the privacy policy changes, change them too. The privacy policy must say what the code does (what is stored, that nothing is sent, what the content script reads): both stores' reviewers check it against the permissions.
- **Firefox's `chrome.*` is callback-only**: with no callback it returns `undefined`, even for APIs that exist there (`chrome.scripting.executeScript`). Awaiting it silently yields nothing, and the popup read every puzzle page as "No puzzle detected" on Firefox until this was found (in Firefox 157, with a real toolbar click). Use `browser.*` for promises; the Chrome polyfill supplies `browser.*` but has no `scripting`, so `extractPuzzleIdFromDOM()` uses `browser.scripting` when it exists and falls back to `chrome.scripting` (promise-based in Chrome MV3). Two popup tests give it each browser's shape. Callback-style `chrome.*` calls (`content.js`, `chrome.tabs.query/update` in the popup) are fine on Firefox.
- New runtime files must be added to the `INCLUDE` list in BOTH `scripts/package.js` and `scripts/package-firefox.js`.
- **Pause / resume (one paused cycle per category)**: a paused cycle is *parked* in the top-level storage key `pausedCycles` (`{ [category]: cycle }`, "All Categories" is its own key, the key is removed when empty), and `trainingSession` only ever holds the cycle that is running (or showing the score screen). `pausedAt` on a cycle is a freeze point for the clock like `cycleFinishedAt`: `getElapsed()` stops at it, the interval doesn't tick, and Lichess's Continue, auto-next, the jump watcher and `advance()` all ignore the page while the cycle is paused. **Pause** (`pauseTraining`) parks first and empties the active slot second (so nothing is lost between the two writes); `saveSession` routes any session with `pausedAt` to the parked area (never the active slot, which minimizing a paused overlay once re-created as a running cycle); the overlay stays up from the in-memory copy (the storage listener ignores the removal while `session.pausedAt`). **The paused look is the normal panel, not a separate screen**: `.wpk-body.wpk-paused` keeps every row and button in the same place (a test compares their boxes before and after pausing, within 1px, so anything added for the paused state must fit inside the line it sits in, as the `.wpk-paused-tag` does with `line-height: 1`), and only signs change: title `Paused`, amber progress bar and tag, Auto-next disabled and dimmed, Skip `aria-disabled` (advance() is the real guard), and `.wpk-btn-pause` is replaced by the green `.wpk-btn-play`, which is 34px at rest and grows leftwards to show `Continue` on `:hover`/`:focus-visible` (as the popup's Save/Train do). The pill swaps its dumbbell for ⏸. Restart while paused (`restartCycle`) confirms, then clears `pausedAt`, takes ownership, saves to the active slot, unparks, and navigates to puzzle 1. **Continue** (overlay `resumeTraining` or popup) shifts `timerStartedAt` forward by the paused duration (so paused time is excluded from the overlay *and* the recorded `timeTaken`), writes the cycle to the active slot, *then* removes only that category from `pausedCycles`, and loads the puzzle fresh. **Close** only removes the overlay (the title-bar X is Close while paused); after a reload nothing is active, so nothing shows: the way back is the popup (row tag `⏸ n/total`, and pressing Train on that category continues it straight away: `startTrainingSession` takes only that category's parked cycle with no prompt; the popup has no Restart, so starting a parked cycle over means continuing it and using the overlay's Restart, which asks first and never touches `lichessNotes`). Starting another category never touches a paused one. **Pressing Train (a category or Train all categories) while another cycle is running just starts the new one, with no question**: it replaces the running cycle, whose unfinished progress is dropped without a record (Pause is how to keep a place); the old "A training session is already in progress. Start a new one?" `confirm()` is gone, and the popup uses no native dialog at all. **Pause is offered on Train all too, on purpose**: a Train-all cycle is parked under the `All Categories` key like any other, and a test pauses one in the overlay and continues it from the popup's Train all button. The popup shows a waiting Train-all cycle only in that button's tooltip (categories get a visible `⏸ n/total` tag), which can make it look as if nothing was saved. A cycle paused in the old shape (`trainingSession.pausedAt`) is parked by the popup on the next start. `renameCategory` moves a parked cycle to the new name and `deleteCategory` drops it (inside the background's queue, like every change to the parked map). Known gap: renaming a category whose cycle is *running* still ends it (the overlay finds no category by the old name).
- **Import** merges a file written by Export (`{app: "lichess-puzzle-saver", exportVersion: 1, data: {categories}}`; categories and puzzle IDs only, so every existing export imports) into storage and never removes or overwrites anything. All validation lives in the background's pure `planImport()`, which both `IMPORT_PREVIEW` (what the options page shows before confirming) and `IMPORT_APPLY` use, so the preview and the result agree. A wrong file is refused with a reason (wrong `app`, `exportVersion` newer than 1, no categories, too many categories/puzzles, nothing usable); bad names (the rule is the background's one `validCategoryName()`, shared with create and rename, so the three cannot disagree: text only, 1-60 characters after trimming, not `__proto__`, not the reserved `All Categories` in any case; plus non-list values) and bad IDs (not 5 letters/digits) are skipped and counted, not fatal. Existing categories are matched case-insensitively using own keys only (never `in` or indexing, which would see `constructor`), new ones get the least-used colour like `createCategory`, and a file that adds nothing writes nothing. The options page refuses files over 2 MB before reading them. If the export file ever gains fields, bump `exportVersion` and keep reading version 1.
- **Session ownership**: `trainingSession.ownerTabId` ties the session to one tab (the popup sets it to the tab Play is pressed in). The background decides each tab's role in `sessionRole()`, the only place that can check the owner is alive (`tabs.get`): `owner` runs the overlay as before; `other` (a live tab owns it) and `none` do **nothing**, no overlay and no listeners; `resumable` (owner closed, browser restarted, stale id, or a session saved before ownership existed) shows only a Resume chip, and claiming it (`CLAIM_SESSION`, compare-and-set) reloads the tab as the owner at the session's current puzzle. `tabs.onRemoved` / `runtime.onStartup` release the owner (the liveness check is the safety net). An owner listens to `storage.onChanged` and `detach()`es (stops everything, keeps the stored session) when the session is ended or handed to another tab. Never let a non-owner write `trainingSession`: a stale in-memory copy silently erased the other tab's progress before this existed. The Chrome polyfill had to grow `tabs.get`, `tabs.onRemoved` and `runtime.onStartup` for this.
- **Overlay tooltips**: any element with `data-tip` shows it on hover or keyboard focus (`:focus-visible` only, so a mouse click doesn't repeat the hover; Escape dismisses). It is ONE `.wpk-tooltip` element kept outside `.wpk-panel`, because the panel has `overflow: hidden` and would clip a CSS-only tooltip; it is placed above the button, below it when there is no room, and nudged sideways to stay on screen, and `render()` re-attaches it after clearing the overlay. Don't also set `title` on overlay buttons (a second, native tooltip would stack on ours); put the same words in `aria-label`. Controls are two rows of 34px buttons: the timer and the icon-only Pause (its `aria-label` is its name), then Settings on the left with Restart (`.wpk-btn-restart`, was Reset) and the muted-blue Skip (`--wpk-skip-*` variables, the same in both looks) on the right. Restart asks before discarding the cycle's progress, with an in-overlay question (`askRestart()`, `.wpk-confirm`, laid over the bottom of the panel so nothing moves, Cancel focused by default, Escape cancels) and **never `window.confirm()`**: a native dialog can be suppressed (background tab, "prevent more dialogs") or auto-dismissed by automation, and is then answered "no" unseen, so Restart silently did nothing (this happened in the manual Playwright browser, which has no `dialog` listener). A test fails if a native dialog appears. Icons are inline SVG as static strings: no `${}` in an `innerHTML` template, and no ternary as the assigned value (assign a plain template in each `if`/`else` branch), or the AMO linter warns.
- Overlay colours live in `--wpk-*` variables on `#lpn-woodpecker-overlay`; `.wpk-light` overrides them. Bright `--wpk-accent/danger/warning` are for *text*; buttons carrying white text use the darker `*-solid` variants. A test computes the WCAG contrast of every text/background pair in both looks (4.5:1, 3:1 for the big score), so a new colour or element must pass it.
- **Puzzle ID is read from the DOM only**: `extractPuzzleIdFromPage()` (popup.js) finds an `<a href="/training/<5 chars>">` whose text is exactly `#<the same 5 chars>`. No URL is read or parsed anywhere (the old `IS_TRAINING_PAGE` host/path gate is gone). Verified against live pages: a puzzle, `/training`, `/training/daily` give an ID; the themes list, home page (Puzzle of the day), Storm, Streak, analysis and a non-Lichess site give null. Cost of dropping the gate: the injected function now also runs on whatever tab the popup is opened over (activeTab, read-only) and a non-Lichess page that fakes that exact markup could feed a 5-character ID into the save flow (still strictly validated, only saved on a click).
- **Branding: `icons/logo.svg` is the one source of every brand image** (toolbar and store icons, favicon, the logo in the popup, the settings page and the overlay). Never draw or paste another logo. `npm run generate-icons` (a dev tool: it rasterises the SVG with Playwright, so nothing new ships) writes `icons/icon16/32/48/128.png` and rewrites the single line between the `LOGO:BEGIN`/`LOGO:END` markers in `content.js`; commit what it produces whenever the logo changes. The logo's navy base vanishes on a dark surface, so it is **always shown on a light rounded tile** (the logo's ivory): baked into the PNGs, and `.logo-tile` / `.wpk-logo` in the pages and the overlay. The popup and settings pages use the file as a plain `<img src="icons/logo.svg">`; **the overlay inlines it** (via `makeLogo()`, parsed with `DOMParser`, ids prefixed `wpk-`) instead of loading it, because a file the page could load would have to be listed in `web_accessible_resources`, which would let lichess.org detect that the extension is installed. `npm run check` fails if a file the manifest or a page loads is missing from the `INCLUDE` lists (a forgotten logo would ship as a broken image), and a test fails if the overlay's inline copy drifts from the file.
- Keep it dependency-free at runtime; dev tooling lives in `devDependencies` only.

## Workflows (in `.claude/`)
- `/verify` — check + test + diff risk summary. Run before declaring work done.
- `/extension-qa` — Playwright MCP exploratory pass in a real browser with the extension loaded.
- `/release` — version bump, packages, store checklist, tag.
- `e2e-runner` agent — runs/fixes Playwright tests in its own context.
- `code-reviewer` agent + the **review gate**: a read-only, fresh-context subagent (Sonnet) that reviews the pending changes against this file's rules and ends with a `## Review Summary` (CRITICAL/HIGH/MEDIUM/LOW counts and a verdict). It follows ECC's reviewer (confidence filter, "cite the exact line or drop it") with a checklist for this extension. Unlike ECC, where review happens only if Claude follows a rule, hooks make it mechanical (`.claude/hooks/review-gate.js`, three hooks: `PreToolUse` on Bash = `gate`, `SubagentStart` = `start`, `SubagentStop` = `mark`, the last two matching `code-reviewer`). `gate` denies a commit while the **code files** (every `.js`, `.css` and `.html` file at the repo root, so a new file such as `shared.js` is covered the day it is created and cannot be forgotten in a name list; manifests and package.json without their `version`, scripts, tests, workflows, `playwright.config.js`, and the files that make up the gate, the reviewer and the QA tooling: `.claude/settings.json`, `hooks`, `agents`, `skills`, `.claude/playwright-mcp.json`, `.mcp.json`) differ from what a review last covered; docs, listings, images and lock files never trigger it. It reads the command properly (quotes respected, heredoc bodies and `#` comments skipped, `\` line continuations joined, `/usr/bin/git`, `sudo`, `xargs`, `-C dir` / `-c k=v` options, `env`, `( )`, `sh -c`) so that text which merely mentions a commit does not trip it. `start` records the code as it is when the reviewer launches, and `mark` credits exactly that to it, so an edit made while it runs is not counted as reviewed; `mark` finds the reviewer's report in the stop event's `last_assistant_message` and, because a real run did not send that field (the docs say it should), in the last assistant record of the event's `agent_transcript_path`, where it arrives as plain text or as the message of a `SubagentHandback` call; it records only if the reviewer ended with its summary **and its last `Verdict:` line says APPROVE (or APPROVE WITH NOTES) without BLOCK**, whatever markdown decoration it wears; BLOCK, a missing verdict, or a line listing every option credits nothing. **The flow when it blocks: run the `code-reviewer` subagent; if it says BLOCK, fix every CRITICAL and HIGH finding (or tell the user why not) and run it again on the fix; commit once a review ends APPROVE or APPROVE WITH NOTES; tell the user the MEDIUM and LOW findings.** Escape hatch: `WP_SKIP_REVIEW=1` as a prefix of the commit itself (text elsewhere in the command does not count). It fails open (an error, a non-git directory or an unreadable event lets the commit through) and keeps its state in the git-ignored `.claude/.review-state.json` / `.review-pending.json`. Known limits: it covers commits made through Claude's Bash tool, not your terminal; a review of only part of the code still marks all of it (the hook cannot know the scope); a commit aimed at another repository is judged by this project's code; a commit inside a backtick or `$(...)` substitution is not seen; two reviewers running at once share one start record (the second is credited with the code at its own stop); a missing `start` hook degrades to crediting the code at stop time rather than blocking forever; a review that runs longer than 30 minutes, or one that finds no start record, is credited with the code at stop time; a `<<` inside `$((...))` arithmetic can hide the rest of a command; `sh -c "..." _ arg` with trailing arguments is not looked into; and `mark` needs `agent_type` plus either the report or a readable transcript on `SubagentStop` (otherwise nothing ever unlocks: use the escape hatch, and look at what the event carries, since the hook events are the part most likely to change between Claude Code versions). `/review [range]` runs the same reviewer on demand. `tests/review-gate.spec.js` tests the hook in a throwaway repo, each rule with a negative control. New hooks in `settings.json` may need approving in `/hooks` or a restart before they take effect, and a newly added agent is only callable after a restart.
- A hook syntax-checks every edited `.js`/`.json` automatically.
- CI: `.github/workflows/ci.yml` (check + lint + e2e, plus weekly live-Lichess run), `release.yml` (tag `v*` → GitHub Release with both packages).

## Testing notes
- `runtime.onStartup` does not fire when Playwright relaunches Chromium with `--load-extension`, so tests of an *active* cycle's ownership across a restart can't rely on it. The pause restart test (`a paused cycle survives closing and reopening the browser, and continues from the popup`) doesn't need it: a parked cycle has no owner, so it checks the parked cycle survives and Continue works from the popup.
- Playwright auto-dismisses native `alert/confirm/prompt` dialogs when the script has no `page.on("dialog")` listener, and `manual-browser.js` (the browser handed to the user) has none. So a `confirm()` there is answered "Cancel" instantly and looks like a dead button. Neither the overlay nor the popup nor the options page uses `confirm()` for that reason (a test in each fails if a native dialog appears).
- Tests open training pages with `gotoTraining()`, which claims the session through the Resume chip the way a real first visit would, so the claim path runs in every overlay test. Seed sessions with `ownerTabId: null`. The popup's Play (which sets `ownerTabId`) can't be driven, so check it by hand.
- Tests: `tests/*.spec.js`; only `tests/fixtures.js` is browser-specific (so a Firefox fixture can be added later).
- Branded Chrome 137+ ignores `--load-extension`; always use Playwright's bundled Chromium.
- If the overlay test fails, first suspect a Lichess DOM change or network, not the extension.
- The popup's save flow (toolbar icon -> detect tab -> inject `extractPuzzleIdFromPage` -> Save) cannot be driven end to end: no automation can open a browser-action popup, `popup.html` opened as a tab sees itself as the active tab, and `scripting.executeScript` on lichess.org is refused ("manifest must request permission to access this host") because `activeTab` is only granted by a real toolbar click. Tests cover the pieces instead: the shipped extraction function against live markup, and `tests/popup.spec.js`, which opens `popup.html` as a tab, sets `currentPuzzleId` and calls `renderAll()` (it is a global, as is `loadData`). Check Save in the real popup by hand before a release. Tests that start a session (Train) must read storage through a second extension page, keep the popup tab active and stub `window.close` (see `trainingSetup`).
- Firefox at runtime has no automated test, but it *can* be driven: Firefox 157 starts with `-marionette --remote-allow-system-access` and a throwaway profile, `Addon:Install` loads a zipped copy of the extension (with `manifest-firefox.json` as `manifest.json`) temporarily, and from the chrome context `window.CustomizableUI.getWidget("lichess-woodpecker_extension-browser-action")` plus `window.gUnifiedExtensions.togglePanel()` and a click on its `.unified-extensions-item-action-button` is a real toolbar click (so `activeTab` is granted). The popup can't be read from outside, so a debug copy posts what it saw to a local port. Checked this way: popup detection, creating a library, claiming a session from the Resume chip, the overlay panel and Skip. Not checked: export, import, clear stats, the options tabs and the stats pagination on Firefox (all covered on Chromium, including a real export from one profile imported into another). Advancement and stats are covered with fixture pages served over the real lichess.org URLs (`context.route`), built from markup recorded live.
- Correct vs incorrect comes from Lichess's DOM, read at Continue time: the session strip's current entry `.puzzle__session a.current` gets `result-true` (clean solve) or `result-false` (any wrong move, or View the solution). The strip is absent on a direct puzzle URL in a fresh browser profile (verified), so the fallback is a common path, not a corner case: correct iff the move list has no `move.fail` and has a `move.win` (viewing the solution never sets `win`). The strip shows the previous attempt's value at page load and is rewritten at completion, so never read it early. The end-of-puzzle text says "Success!" for a clean solve and for a solve after a mistake, so don't use it. A Lichess DOM rename here shows up as every puzzle counting incorrect.
- Overlay theme: `pageIsLight()` judges the Lichess page by its computed background colour (walks up from `main`; on real Lichess the colour is on `<body>`: `rgb(237,235,233)` light, `rgb(22,21,18)` dark), never by Lichess's class or variable names. Transparent/image themes keep the dark look. Re-checked on `<html>`/`<body>` attribute and `<head>` changes (plus 500ms later, since the class flips before the stylesheet loads) and on the OS colour-scheme change. Overlay semantics: region role + label, aria-labels on the icon buttons, the pill is a focusable button, `:focus-visible` rings.
- Auto-next: `maybeAutoAdvance()` runs from one `MutationObserver` (`finishedWatcher`, created once; never create observers per render, that's what once made one Continue click skip three puzzles). When `.puzzle__feedback.after` is showing and `firstTryCorrect()`, it advances after `AUTO_NEXT_MS` (1s) and **re-checks the verdict when the timer fires**, because the strip can still hold the previous attempt's mark at the instant the panel appears. Incorrect puzzles never auto-advance (they're the ones to study); clicking Continue still works at any time. The `autoNext` storage key (absent = on) is toggled by the overlay checkbox. Lichess's own "Jump to next puzzle immediately" setting (`puzzle.autoNext` in its localStorage) swaps in a random puzzle ~0.3s after a finish, same page, URL by pushState, so it beats our 1s pause (recorded live) and our script keeps running on a puzzle outside the session. `watchPage()` handles it: while the finished panel shows it remembers the verdict, and if `location.pathname` then changes it counts that puzzle and navigates to the session's next one, whatever our switch says. With that setting on, a mistake cannot wait for you to study it; the README tells users to turn it off.
- Cycle end: `advance()` doesn't roll over by itself. It sets `session.cycleFinishedAt` (which freezes the timer via `getElapsed()` and switches the overlay to the score screen), saves the stats record right then, and navigates nowhere. The score screen (`renderResultsBody`) keeps the overlay's frame: the normal title bar (so minimize and ✕ still work, and the title stays "Woodpecker Training"), the same panel width, and the bottom row of the training view (`makeSettingsButton()` gear on the left; **Exit** and **Repeat** (starts the next cycle; its label is just "Repeat", the header already says which cycle just ended) in the places Restart and Skip occupy, at the same 34px height), with the content in between: a green check, "Cycle N Complete", "category · N puzzles processed", three figures (Correct green, Incorrect red, Skipped amber: the same colour system as the Statistics table, and now the training stats row too), then the first-try accuracy and time-taken rows. Its background is the panel's own theme colour; nothing paints a fixed one. **A scene plays behind the content, for as long as the score screen is up** (`makeCelebration()`, `.wpk-fx`), by first-try accuracy: **fireworks with confetti at 100%** (`data-fx="fireworks"`: four bursts, each a rocket and two rings of sparks, that loop at different spots and colours), **sparkles above 75%** (golden four-point stars that swell and fade over a warm glow, a few big), **floating particles from 50% to 75%** (soft blue orbs rising and drifting over a cool glow; 75 itself is particles, 76 is sparkles) and a **storm below 50%** (three drifting cloud banks, 56 wind-slanted raindrops in two depths, the panel darkened, and one dim lightning pulse every 7s). It is decoration only, and these are rules, each pinned by a test: it sits at `z-index: 0` behind the content, has `pointer-events: none` (never blocks a button), is `aria-hidden` and clipped to the panel; it is not created at all under `prefers-reduced-motion: reduce`; it is built whenever the score screen is rendered and gone when it is not (minimizing removes it, reopening builds it again, there is no timer and no once-only gate); every piece loops (`infinite`) in CSS and animates **only `transform` and `opacity`** (so the GPU does it, no per-frame script, no `requestAnimationFrame`; a probe measured 60fps with every scene in headless Chromium, the same as with none; that says little about real GPUs, battery or Firefox, and a scene keeps running on an idle tab, though browsers throttle hidden ones) and a scene stays within about 130 elements; the lightning, the only flashing thing, is one pulse of at most 0.22 opacity every 7s (far under the three-flashes-a-second limit). The generic piece rule uses `:where(.wpk-fx)` so it stays weaker than each piece's own class rules (an element selector once overrode the lightning's 7s with 3s, which a test caught). Colours are `--wpk-fx-*` variables with a light-page set (kept faint there: the storm's clouds and gloom sit behind the muted text, and the contrast test measures the plain panel, not the scene, so keep them light), and the fireworks use saturated mid-tones (pale tints vanish on a white page). Plain CSS animations on generated spans: no canvas, no library, no `innerHTML`. The Repeat button (`startNextCycle()`) does the reshuffle/reset; Exit calls `endSession()`. While `cycleFinishedAt` is set, Lichess's own Continue is swallowed. The field lives in the saved session, so a reload comes back to the score screen.
- Get a hint (recorded live): Lichess scores hint + clean solve as `result-true`, so it counts **correct**; hint + wrong move and hint + View the solution are `result-false`, so **incorrect**. The hint leaves no trace by the end screen (the first `.view_solution button` only loses `button-empty` while hinted, and resets after a wrong move). Counting a hint as help would mean tracking that click during play and persisting it in the session, since a reload mid-puzzle loses in-page state.
- **The background is the only writer of `lichessNotes`, and applies changes one at a time** (`serialized()`, a promise queue; `npm run check` fails if `popup.js`, `options.js` or `content.js` write the key directly). Every change was read-all, change, write-all, so two at once (a Save in the popup while the overlay recorded a cycle, an import during a rename) let the later write throw the earlier one away; tests fire dozens at once and check every one survives. Reading never writes: `getAllData()` returns the defaults in memory when nothing is stored, **throws** when the read fails (the change is refused; it used to carry on from defaults and save them over the library, so one transient storage failure could wipe it all), and when what is stored is not a library it first copies it to `lichessNotesBackup`. The queue is in memory, which is fine: a change is only ever queued while the worker is running. **The parked map of paused cycles (`pausedCycles`) is changed only by the background too**, as operations applied to the map as it is at that moment, never as a whole map written back from an earlier read: `PARK_CYCLE` and `UNPARK_CYCLE` (the overlay's Pause and Continue) and `START_SESSION` (the popup: sets the running cycle and parks an old-shape paused one and/or takes the continued one out, in one write). Each cycle is validated (`checkCycle`), including that every queue entry is `https://lichess.org/training/<id>`, because the overlay navigates to those and nothing else is a place to go; `npm run check` fails if a page or the overlay writes `pausedCycles` directly. `trainingSession` (the *running* cycle) is still written by the tab that owns it: the ownership model, not the queue, keeps that one straight, and a stale save from a tab that is being handed over is a known, millisecond-wide residual. `RECORD_STATS` validates the record (known fields only, finite non-negative numbers, name length) and keeps the newest 50. **The background does not trust its callers**: `handleMessage(message, sender)` refuses everything except `RECORD_STATS`, `GET_SESSION_ROLE`, `CLAIM_SESSION` and `OPEN_OPTIONS_PAGE` unless the sender is one of the extension's own pages (`sender.url` under `runtime.getURL("")`), so a content script, which lives in a web page's process, cannot change the library even if the page compromises it (a test calls `handleMessage` with a fake overlay sender through the service worker). A category must be a string and an *own* key (`hasCategory()`, never `in`, which is true of `constructor`, and never a coerced list), and `ADD_PUZZLE` / `REMOVE_PUZZLE` check the ID's format (`isPuzzleId`) themselves, not only the popup and import.
- First-time setup: `npm install && npx playwright install chromium`, and for the Playwright MCP (bundles its own Playwright version) `npx @playwright/mcp@0.0.83 install-browser chromium`. Bump the MCP pin in `.mcp.json` deliberately; a new version may need a new browser build.
- Chrome storage returns object keys in its own order; compare storage read-backs canonically, not with plain `JSON.stringify`.
